# AGENTS.md

Read this first. It holds the decisions behind this project and the rules for changing it. It is written for coding agents (Claude Code reads it through `CLAUDE.md`; Codex, Cursor, Copilot and others read `AGENTS.md` directly) and for people.

It sits on top of the human docs and doesn't repeat them: [CONTRIBUTING.md](CONTRIBUTING.md) covers setup and adding a check; [docs/architecture.md](docs/architecture.md) covers how a scan works; [docs/releasing.md](docs/releasing.md) covers releases; [docs/deployment.md](docs/deployment.md) covers running it.

## Keep this file current

This file is part of the code. It is only useful while it is true, so every change keeps it true:

1. **In the same commit** as any change that makes, changes or reverses a decision, update the section it affects and add a dated line to the [decision log](#decision-log). Examples: a supported version, a dependency or tool choice, a UX pattern, a security rule, a release or process step, or a preference the maintainer stated in a session.
2. **Edit, don't append contradictions.** When a decision is reversed, rewrite the rule where it lives, and change the old log line to say it was superseded and by what. No two lines of this file may disagree.
3. **Link, don't copy.** When the detail lives in a doc or in code, point to it. Copies go stale.
4. **Check it.** `test/agents.test.ts` fails when this file names a path that doesn't exist or an `npm run` script that isn't in package.json, when the Node.js version here doesn't match `src/node-check.ts`, or when `CLAUDE.md` stops importing this file. `npm run check` runs it.
5. **Before you finish a task,** reread the [decision log](#decision-log) and the sections you touched, and ask whether your change belongs in either. If the maintainer told you how they want something done, record it under [Working with the maintainer](#working-with-the-maintainer). A contributor's own preferences don't go in this file (see [Working with a contributor](#working-with-a-contributor)).

## What Keelson is

A self-hosted, **read-only** security posture tracker for **Cloudflare, Vercel and AWS** (more providers, such as Google Cloud and Google Workspace, are planned). You give it a credential per platform (a token, or an access key for AWS), and it scans daily. The web app lets you triage every finding until it is fixed. It ships only as a Docker image (`ghcr.io/r4reetik/keelson`), run on a laptop or for a team on a server, ECS or Kubernetes. It is open source (MIT) and published to GHCR from GitHub Actions; nothing is published to npm.

The name is for where it is going: beyond edge and network settings to code (GitHub repositories), where that code is deployed and reachable from, cloud activity (CloudTrail, VPC flow logs), later runtime security, and an AI penetration tester that can work white box from all of that, or black box. None of this is built yet; design today's changes so it can be added.

It is built for many accounts, grouped into **entities**. An entity is a company, legal entity or team, and can hold accounts on several providers (its Cloudflare accounts, Vercel teams and AWS accounts together). Entities can be different companies, so their data, alerts and suggestions never cross. Each entity chooses whether it appears in the combined "All accounts" view (`includeInAll`). People may use one platform only: nothing may assume Cloudflare, or any other provider, is connected.

### Providers

- **Every account belongs to one provider** (`accounts.provider`; `src/shared/providers.ts` lists them). Everything provider-specific goes through the `Provider` interface (`src/providers/types.ts`), registered in `src/providers/index.ts`. The scanner, account routes and setup screen never branch on a provider by name. How to add one: [CONTRIBUTING.md](CONTRIBUTING.md#adding-a-provider).
- **Nothing compares a provider's name.** What the app says about a provider comes from `PROVIDER_INFO` in `src/shared/providers.ts`: its label, its words for an account, a resource and a credential, the credential's fields, its API host, what its dashboard is called. The few per-provider pieces of UI and docs are records keyed by provider ID (`TOKEN_HELP` in `web/src/components/connect.tsx`, `PROVIDER_GLYPH` in `web/src/components/ui.tsx`, `SOURCE_REGISTRY` in `scripts/docs.ts`), so a new provider doesn't compile until it has an entry. Don't write `provider === "…"` anywhere, and don't write copy that lists providers by hand: use `providerList()`.
- **Layout.** New providers get `src/providers/<id>/` (client, sources, inventory, checks, catalog, engine, views, permissions), like `src/providers/vercel/` and `src/providers/aws/`. Cloudflare predates this and stays in `src/core`, wrapped by `src/providers/cloudflare.ts`; the engine, check format and categories in `src/core` are shared by all providers.
- **One check format, one engine.** Provider checks are written with `checksFor<Context, SourceKey>()` and summarised by `summarize()` in `src/core/engine.ts`. Categories are one shared list (`src/core/categories.ts`); add one only when no existing category fits. IDs carry a provider prefix (`V…` for Vercel, `A…` for AWS) and are unique across providers. The full catalog is `src/providers/catalog.ts`.
- **A finding's `zone` is the provider's unit of grouping**: a Cloudflare zone, a Vercel project's name, an AWS region (or "Global" for IAM, S3 settings, CloudFront and Route 53). Grouping, filters and links work the same for all of them; the UI names it from `PROVIDER_INFO.resource` (`zoneWord`).
- **Checks that span providers** (`XP-…`) compare an account with the other accounts in its entity through `links` stored in each scan's snapshot (`ProviderLinks`, `LINK_KEYS` in `src/shared/api.ts`) and passed as `related`. The scanner merges every list generically, so a new one needs no scanner change (name its publisher in `LINK_PROVIDER`). A scan leaves a list out when it couldn't read all of it, and a merged list is only used when every account of the publishing provider in the entity supplied it; otherwise it is null and named in `related.unknown`, so a check on the same provider can tell "no other account" from "another account we know nothing about". The checks never look outside the entity, and are skipped (not passed) when the entity has no scanned account on the other provider. See [docs/architecture.md](docs/architecture.md#checks-that-span-providers).
- **A view is a set of accounts**, named by a scope key (`src/shared/scope.ts`): `all`, `e:<entity>`, `a:<account>`, any ticked set `s:<id>,<id>`, and `@<provider>` to narrow one of the first two (`e:3@vercel`). Every scoped API, export, report and link follows the key. `keyForAccounts` gives a set its shortest key, so the whole of an entity is still `e:3`. A set may span entities only when all of them are shown in All accounts.
- **The two pickers are tick-box trees over that one set** (`ScopeSwitcher` and `ProviderSwitch` in `web/src/App.tsx`): entity → accounts, and platform → accounts. Ticking a parent ticks its accounts, the last account can't be unticked, and the menu stays open while ticking. There is no separate "all of this entity" row: the entity's own box is that. The platform picker shows only when the entities in view have more than one platform, and works for any number of platforms and accounts.
- **Scores:** each account is scored on its own checks; a view's score is the mean of its accounts' scores, and with several providers in view the Overview also shows each provider's mean (`providerScores`).
- **Vercel API facts learned from a real team** (the OpenAPI description doesn't say them):
  - Managed rulesets (bot protection as `bot_filter`, `ai_bots`, `owasp`, `vercel_ruleset`) live on the project in `security.managedRules`, not in the firewall configuration. The firewall configuration holds custom rules, IP rules and the OWASP core ruleset (`crs`, per attack type).
  - A project that was never configured has no `security` block and its firewall configuration answers 404. Vercel's defaults apply: firewall on, managed rulesets off.
  - Someone invited appears both in `emailInviteCodes` and as a member with `confirmed: false`.
  - A token scoped to one team gets 400 from `/v6/user/tokens`; only a Full Account token can list tokens.
  - Team two-factor enforcement is `mfa.enforced` on the team.
  To check a shape against a real team, use a throwaway script that sends GET requests only and prints keys and counts, never values or the token.
- **AWS, as built** (checked against two real accounts on 2026-11-10: every source was readable and parsed; the Lambda function-URL and public snapshot and image answers had nothing in them, so those shapes are still from the API references only):
  - Every request is a signed GET. The Query APIs (IAM, STS, EC2, RDS, load balancers) take their action in the query string; S3, CloudFront, Route 53, Lambda and GuardDuty are REST. Services whose APIs only answer POST (CloudTrail, KMS, Config, ACM, Organizations) are not read. Reading them needs a decision on the GET-only rule first; don't add POST quietly.
  - No AWS SDK: `src/providers/aws/sigv4.ts` signs with `node:crypto` (tested against AWS's published example signatures) and `xml.ts` reads the XML answers.
  - The credential is one long-lived access key, stored in the vault as `<key ID>:<secret>`. A key belongs to one account, so `listAccounts` returns that one. Temporary keys (ASIA…) are refused; assuming a role into other accounts isn't supported yet. The key's user should have only AWS's managed SecurityAudit policy.
  - Regional sources are read in every enabled region. A region that refuses the key (a service control policy) is skipped and recorded (`skippedRegions`), not a coverage gap, unless every region refuses. A bucket that refuses is left out the same way.
  - Per-region settings (GuardDuty, EBS encryption by default, flow logs) are judged only where something runs, so empty regions and unused default VPCs don't produce findings.
  - Policy documents are reduced to what they allow and never stored; Lambda's environment variables arrive in the function list and are dropped; only the last four characters of an access key ID are kept. Instance start-up scripts (user data) are scanned for credentials in memory with the shared patterns in `src/core/secret-patterns.ts`, and only the kind found is kept. `test/aws.test.ts` checks the stored data.
  - A security group is judged by the network interfaces it is attached to (`DescribeNetworkInterfaces`), not by its rules alone: the check's own severity when something with a public address uses it, one step lower when only private interfaces do, low when nothing does.
  - AWS's public address ranges (`ip-ranges.amazonaws.com`, `src/core/aws-ranges.ts`) are read without the access key, by AWS scans and by a Cloudflare scan whose entity has an AWS account, to tell a DNS record that points at an AWS address from one that points elsewhere.
  - **A dangling record is rated by what can be done with it** (`DANGLING` in `src/core/links.ts`): a missing S3 bucket or CloudFront alias can be claimed (high); a missing load balancer can't, because its name is random (low). An AWS address is only called dangling when Keelson saw it leave the entity: each AWS scan carries an `addressHistory` (held now, released since) from the previous snapshot, passed in as `ScanInput.previous`. An AWS address nobody in the entity ever held is a low-severity note, because on real accounts most of those were vendors' servers and accounts that weren't connected.
  - Things AWS owns on the account's behalf aren't in the account's own lists and look like dangling records if they're missed: classic load balancers (an older version of the load balancer API) and the CloudFront distributions behind API Gateway custom domains. Both are read. Expect more of these (Cognito, Amplify, AppSync); dangling-record findings stay "likely".
- **Provider glyphs are the platforms' own monochrome marks** (`PROVIDER_GLYPH` in `web/src/components/ui.tsx`: the SVG path from Simple Icons, drawn in the text colour, never in brand colours). They only say which platform something is on; the README and the report say Keelson isn't affiliated with them.

## Commands

```bash
npm install
npm run dev -- --mock   # mocked Cloudflare, Vercel and AWS (3 entities, one with all three), nothing written to disk
npm run dev             # real accounts, data in ./.keelson
npm run check           # typecheck + lint/format check + tests: must pass before every commit
npm run format          # fix formatting (Biome)
npm run docs            # regenerate docs/checks.md and docs/permissions.md after changing a check
npm run build           # dist/ (server via tsc, web via Vite)
npm run sync            # maintainer's clone only: catch up with origin/main (instead of git pull), repairing moved release notes
npm run release -- minor --dry-run   # maintainer's clone only: what a release would do; drop --dry-run to cut it
```

API on port 4317, web with hot reload on 5173. Tests are `node:test` and run TypeScript directly (`npm test`). There is no build step for the server in development.

## Hard rules

These are never broken. A test enforces most of them.

- **The scanner only reads.** REST calls are GET. Cloudflare's GraphQL is POST but query-only. `test/integration.test.ts` (Cloudflare), `test/vercel.test.ts` (Vercel) and `test/aws.test.ts` (AWS) fail on anything else. Never add a write call to any provider, even behind a flag. This matters most where a provider can't issue read-only tokens: Vercel tokens can do whatever their user's role allows, so Keelson is what keeps them read-only.
- **Secret values are never read or stored.** Vercel environment variables are listed without `decrypt` and their values dropped; drain and webhook URLs keep only scheme and host; drain headers are dropped. Secrets are judged by name, type and Vercel's own flags. AWS policy documents and Lambda environment variables are dropped as they're read. `test/vercel.test.ts` and `test/aws.test.ts` check the stored data.
- **A check whose data couldn't be read is skipped, never passed or failed.** Missing permissions become coverage gaps (`src/core/sources.ts`), not errors.
- **Secrets never leave the vault.** Credentials of every provider (tokens, access keys) are stored in `<data-dir>/credentials.json` (mode 0600), and the database holds only a token ID. No API response, log line, test fixture or screenshot may contain a token, a real account ID, a hostname or an email. `test/server.test.ts` checks the API responses.
- **Entities stay apart.** Alerts go to each entity's own Slack channel or webhook. Owner suggestions come only from the same entity. An entity left out of All accounts stays out of combined views and exports, including a hand-picked set of accounts: `resolveScope` refuses a set that would combine it with another entity. Anything new that aggregates across accounts must respect this.
- **`src/shared` is portable**: no `node:` imports and no DOM. The server returns shared DTOs with `satisfies`, and the web imports them as types.
- **Routes carry their guards** (`src/server/router.ts`): `routes(app).with(requireSession(auth))`. Who can reach a route never depends on where it is registered.
- **Migrations are append-only.** New ones go at the end of `MIGRATIONS` in `src/store/db.ts`, ship only in a new release line, and their fingerprint goes in `test/migrations.test.ts`. Never edit a shipped migration.
- **Don't quote a total check count** in the README, the docs, images or the changelog. It goes stale with every new check.

## Node.js, the image and tooling

- **Keelson ships only as a Docker image** on GHCR, for `linux/amd64` and `linux/arm64`. Nothing is published to npm: package.json is `private`, and `test/env.test.ts` fails if the release workflow publishes to npm. Docs and the in-app upgrade steps describe the image and its release-line tag; running from a clone (`npm start`) is for development and gets `git checkout` steps.
- **The image stays small.** Its final stage is Alpine with only the Node.js binary copied from `node:26-alpine` and the libraries Node's own Alpine image installs for it (libatomic and libstdc++; the build runs `node --version` to catch a missing one): no npm, Yarn or Corepack, which also keeps their dependencies out of image scans. Keep the two Alpine versions in the Dockerfile equal. The build stage runs on the build machine's platform, so runtime dependencies must be plain JavaScript (tested). CI fails when the image passes 200 MB, contains npm, or doesn't run as uid 1000 (the uid earlier images used, so `/data` volumes stay readable). Weigh any new runtime dependency or OS package against that.
- **Node.js 26 LTS only.** The minimum is 26.13.0, the first Node 26 LTS release. `NODE_MAJOR` and `MIN_NODE` in `src/node-check.ts` are the source of truth, and `engines` in package.json says the same (tested). `.nvmrc` says `26`, the image runs `node:26-alpine`'s binary, and CI tests on 26. `src/bin.ts` runs `checkNode` before importing anything else, so a clone run on an older Node.js prints the upgrade command for the user's Node manager (nvm, fnm, Volta, Homebrew, winget). `src/node-check.ts` imports nothing, so it runs on old Node.js; don't add imports to it.
- Biome 2.6 is used for both lint and format (`biome.json`: 2 spaces, 160 columns, double quotes, trailing commas). TypeScript runs with type stripping, so use `.ts` extensions in imports and no enums or namespaces.
- Dependabot ignores major updates of `@types/node` and the Docker `node` images (`.github/dependabot.yml`). Those move together with `NODE_MAJOR`, by hand.
- GitHub Actions use current majors (checkout and setup-node v7, CodeQL v4, Docker actions v4–v7).
- **`.claude/settings.json` is shared** with everyone who uses Claude Code here. It lets the checks, tests, formatting, docs, build and the mock dev server run without a prompt, and denies `npm run release`, `npm run sync` and reading `.keelson/` (real scan data and tokens). Keep it to commands that are safe on any clone; personal permissions go in `.claude/settings.local.json`, which git ignores.

## Code conventions

- **Settings are `KEELSON_*` variables**, read with `env()` from `src/env.ts`, never `process.env.KEELSON_…` directly. The Docker image sets only `KEELSON_INSTALL=docker`; its defaults (`0.0.0.0`, `/data`) live in `src/env.ts`.
- **Every file starts with a short comment saying what it is and why.** Comments explain *why*, not what the code does.
- **Server:** Hono, with one route module per area in `src/server/routes/`. Request bodies are validated in `src/server/validate.ts` before any write. Scoped routes read `c.get("scope")` (`all`, `e:<id>` or `a:<id>`, resolved in `src/shared/scope.ts`).
- **Store:** SQLite, with one repository per concern behind `Repo` (`src/store/repo.ts`). Triage belongs to the finding's fingerprint (check, account, zone, resource), not to a scan, so it survives rescans. Every triage change is recorded in `triage_events`.
- **Checks:** follow [CONTRIBUTING.md](CONTRIBUTING.md#adding-a-check). Report passes as well as failures. Use `confidence: "likely"` for heuristics and `"confirmed"` for probes. Each new check gets a failing case in `test/checks/cases.ts`. Aim for checks that go deeper than other tools, for example correlations across sources and GraphQL traffic evidence, while keeping the finding text plain.
- **Tests:** every bug fix or feature comes with a test that would have caught it. Server behaviour is tested through the app (`test/helpers/app.ts`, `makeApp`) against the mock Cloudflare (`dev/mock/cloudflare.ts`), mock Vercel (`dev/mock/vercel.ts`) and mock AWS (`dev/mock/aws.ts`). Each Vercel check has a failing case in `test/vercel-cases.ts`, and each AWS check in `test/aws-cases.ts`. The mock data must stay fictional.
- **AWS API shapes** come from the AWS API references (`https://docs.aws.amazon.com/`). As with Vercel, a missing field is unreadable or not configured, never a pass.
- **Vercel API shapes** come from Vercel's OpenAPI description (`https://openapi.vercel.sh/`). Check field names there before reading a new one, and treat a missing field as unreadable or not configured, never as a pass.

## Web UI conventions

The UI follows **Cloudflare's design language** using Kumo (`@cloudflare/kumo`), with Phosphor icons and Tailwind. The maintainer asked for no "AI slop" design: no gradients, emoji, decorative cards or made-up components where Kumo has one.

- **Use the shared building blocks** in `web/src/components/ui.tsx`: `Page`, `Card`, `ListCard`, `SettingRow` and `SettingRows`, `FormGrid`, `DialogHeader`, `PageState`, and the badges. Use the shell state from `web/src/shell.tsx` (`useShell`, `useScopedApi`). Every page is listed in `web/src/routes.tsx`.
- **Alignment is strict.** Fields that share a row line up their labels and controls on one baseline, and descriptions sit below the control (`FormGrid`). Spacing comes from the shared components, not from one-off margins. Lines that meet across panes meet exactly (the sidebar header and the top bar are both `h-14`, border included), text in a card's toolbar, rows and footer starts on one edge, and table headings never wrap (`web/src/styles.css`). An icon beside a title that can wrap sits in the text flow (`inline-flex align-middle`), not in a wrapping flex row, so it never ends up on a line of its own.
- **On phones the top bar keeps the entity's name:** the platform picker and Run scan show only their icons below the `sm` breakpoint.
- **Hierarchy:** an entity name always reads as the parent of its account names (entity, then account). Where accounts from several providers mix, an account name carries its provider glyph (`AccountName`, `ProviderIcon`).
- **Provider-specific pages** declare `providers` in `web/src/routes.tsx` (Zones for Cloudflare, Projects for Vercel, Regions for AWS) and are hidden when no account in view is on that provider. Wording says the provider's own words (`PROVIDER_INFO`: "team" for Vercel, "access key" for AWS's credential, "console" for its dashboard) and never assumes a provider.
- **Onboarding starts with the platform** (`ProviderPicker`, then that provider's `TokenHelp` and `ConnectForm`). Someone on one platform never has to read another's steps. The credential's inputs come from `PROVIDER_INFO.fields` (`CredentialFields`): one for a token, two for an AWS access key.
- **One vocabulary** in everything a user reads: **platform** (Cloudflare, Vercel, AWS; the code says `provider`), **entity** (who owns accounts), **account**, **location** (a zone, project or region: `zoneWord` gives the platform's own word, or "Location" when the view mixes platforms), **check** (a rule) and **finding** (one resource failing a check). `Terms` in `web/src/components/ui.tsx` explains them on the Accounts page; keep it in step with any new term.
- **The nautical theme names modules, never everyday terms.** Keelson's own modules and brand may carry a ship or navy name (for example Sonar for discovery from outside, Boarding party for the AI pentester, Ship's log for cloud activity, Manifest for inventory, Drydock for checks before code ships). Each such name always appears with a plain description beside it ("Sonar: external attack surface"). The vocabulary above, and anything in a finding, alert, export or report, stays plain. Small touches (the logo, empty states, the scan schedule as a "watch", release names) are fine where they don't replace a plain term.
- **A finding says where it is from.** `PlatformMark` shows a finding's, check's or group's platform icon wherever platforms mix, and both sides joined by arrows for a check that compares platforms (`spans` on the check, carried on `Finding`, `FindingBrief`, `FindingGroup` and `CheckRow`). Every `XP-` check declares `spans`; a test fails if one doesn't. Use it in any new list of findings.
- **The sidebar has four sections** (`NAV_GROUPS` in `web/src/routes.tsx`): Posture (every platform), Inventory (one page per platform), Insights (what a platform reports besides configuration) and Manage (Keelson itself). A page limited to some platforms shows their icons next to its name.
- **Filters are grouped by what they narrow**: what the finding is (category, confidence, who reported it, correlation) and where it is (location), with severity, account and the platform switch outside the menu. A chip names what it filters ("Category: DNS").
- **Kumo specifics:** a `DropdownMenu.Label` must sit inside a `DropdownMenu.Group`; outside one, opening the menu throws and blanks the page. give `Tooltip` the button through `render={<Button …/>}`. Wrapping a button in a tooltip trigger nests one button in another. Use `ButtonGroup` for split buttons, and `Autocomplete` for free text with suggestions.
- **Finding dialogs** are at least 75% of the screen width on desktop (`sm:w-[75vw]`). J and K move through the list, and only when focus isn't in a field.
- **Type less, pick more.** When a field asks for a value the app already knows, offer it. Owners suggest the owners already used in the entity (`GET /api/owners`). A new entity name that matches an existing one is caught, and the add-accounts form offers to use the existing entity. The Link URL offers the current address. Apply this to any new field.
- **Actions do what their label says for the current view.** "Run scan" scans the selected account, or the entity or All accounts when that is the view, and its menu offers the wider scopes. Tooltips say what will happen.
- **Bulk edits change only the fields the user touched.** Clearing a field is a separate, explicit choice, and every bulk change can be undone.
- `localStorage` is for per-browser conveniences only (theme, last scope), and every read is wrapped in `try`.

## Writing

The same rules apply to UI copy, docs, changelog and commit messages:

- **Describe Keelson by where it is going, and never claim what isn't built.** The one-line description is "One place for the security of your whole infrastructure", with what it does today said in general terms ("checks your cloud, edge and hosting platforms") and anything planned marked as next. Descriptions never name platforms; the README body and docs list them. It is used in the README, the GitHub description, the image label, package.json and the social card (`docs/images/social-preview.html`).
- **Plain, specific English** for someone running Keelson, not a reviewer. Say what happens and what to do. Write sentences, and avoid jargon and marketing.
- **UI copy** names the thing the user sees. Error messages say what's wrong and the fix ("Mock Group already exists. Pick another name.").
- **Commit messages:** one imperative line that says what changed for the user (for example "Run scan scans the selected account, with a menu for the entity or every account"). No AI attribution or co-author trailers.

## Changelog, versions and releases

- **Every user-visible change adds a line under `## Unreleased` in `CHANGELOG.md`**, in the same commit. Mark it `**Breaking:**` with the steps to take if users must act. The release script refuses a breaking change or a new migration within the same release line.
- **Releases are cut locally with `npm run release -- <patch|minor|major|rc>`** (`--dry-run` to preview). It requires a clean `main`, syncs with `origin/main`, runs `npm run check`, bumps, commits `Release vX.Y.Z`, tags, and pushes `main` and the tag in one atomic push. Before 1.0, breaking changes and migrations are `minor`. The tag starts `.github/workflows/release.yml`, which only publishes: the image to GHCR (`:X.Y.Z`, `:X.Y`, `:latest`; candidates only `:X.Y.Z-rc.N`) and GitHub Releases. Running installations read the release to show updates and breaking-change warnings.
- **The workflow never commits or pushes to `main`** (`test/release.test.ts` enforces it), and there is no "Run workflow" button. When CI made the release commit, every release forked `main` from the maintainer's clone. Don't bring that back.
- **Catch up with `npm run sync`** rather than `git pull`: it merges `origin/main` and moves notes that a merge landed under a released version back to `## Unreleased` (`repairReleasedNotes`), committing the repair. The tests fail while released notes differ from their tag, and point at `npm run sync`.
- Agents never run `npm run release` or `npm run sync`'s merge on their own: releasing is the maintainer's call, and both commit (and `release` pushes).
- The README and `docs/deployment.md` pin the current release line (`ghcr.io/r4reetik/keelson:0.6`). `scripts/release.ts` (`pinLine`) updates them on each new line, so don't edit those pins by hand.
- Releases come only from `main`. Older lines get no backports.

## How to work here

These apply in every session, whoever you're working with:

- **Design for more providers.** Alibaba Cloud, Google Cloud, Google Workspace and others are planned, so UI and code choices should work for any number of providers, not the three there are now.
- **Treat every real account as production.** Use the mock (`npm run dev -- --mock`) by default. Against real accounts, run nothing that writes, never print a token, and delete any scratch copies of `~/.keelson` you make. A Cloudflare token for Keelson is read-only, and an AWS access key should belong to a user with only the SecurityAudit policy; a Vercel token can't be read-only, so Keelson's GET-only rule is what protects it.
- **Accept Vercel tokens quietly**: no warning when the token's user can write (see the decision log).
- Confirm before anything destructive or outward-facing.
- When asked for "everywhere", apply the change across the whole app and its docs, not only the place that was named.
- Verify UI changes in a browser against the mock, not just with tests, and say what wasn't checked.
- No attribution lines (`Co-Authored-By`, "Generated with…") in commits or pull requests.

### Who you're working with

The maintainer, r4reetik on GitHub, works in a clone whose `origin` is `github.com/r4reetik/keelson` and cuts the releases. Everyone else is a contributor, working on a fork, so their `origin` is the fork. When it isn't clear which you're working with, ask once before committing, pushing or recording a preference.

## Working with a contributor

Most people who clone this repository are contributors. In their sessions:

- **Work on a branch of their fork**, never on `main`. Commit and push to the fork when they ask, and open the pull request against `main` of `r4reetik/keelson`. Never push to `r4reetik/keelson` itself.
- **Catch up with the upstream repository** (`git remote add upstream https://github.com/r4reetik/keelson.git`, then `git fetch upstream` and rebase the branch on `upstream/main`). `npm run sync` and `npm run release` are for the maintainer's clone; they merge into and push `main`.
- **Check before you commit.** `npm run check` must pass, every change comes with a test, and anything a user would notice gets a line under `## Unreleased` in `CHANGELOG.md` (see [CONTRIBUTING.md](CONTRIBUTING.md#pull-requests)).
- **Bigger changes start with an issue**, so the approach is agreed before the code is written: a new provider, a new dependency, a change to a hard rule or to the UI's structure.
- **Decisions are proposed, not made.** If the change makes or reverses a decision, update this file and add a decision-log line in the same pull request, and say so in the pull request description. The maintainer accepts the decision by merging it.
- **The contributor's own preferences stay out of this file.** They belong in their personal agent settings (for Claude Code, a CLAUDE.local.md file, which git ignores, or its memory), not in the project's rules.

## Working with the maintainer

Preferences the maintainer stated, which apply only in the maintainer's sessions:

- **Commit only when asked**, and **never push**: the maintainer pushes and runs releases. Branch only when asked.
- The maintainer's Cloudflare accounts are **production** and their token is read-only; their Vercel team is production too. The rules for real accounts under [How to work here](#how-to-work-here) apply in full.

## Decision log

Newest first. One line each: the date, the decision, and why. When a decision is reversed, mark the old line "Superseded" and point to the new one.

- 2026-11-13: Keelson is described as one place for the security of your whole infrastructure, without naming platforms: what it does today in general terms, and code, cloud activity, runtime and AI pentesting marked as next. *Why:* the maintainer wants the description to show the global picture rather than a list of today's platforms; marking what is next keeps it true.
- 2026-11-13: All support for the old name Edgewatch is removed before 0.10 ships: `EDGEWATCH_*` variables, `~/.edgewatch`, `edgewatch.db`, the old browser storage keys and the `edgewatch` image are no longer read or published, and an Edgewatch installation starts fresh. `test/env.test.ts` fails if the old name appears anywhere but the changelog, this log and a shipped migration. *Why:* only one or two people ran Edgewatch, and the maintainer chose a clean start over carrying fallbacks. Supersedes the compatibility in the 2026-11-12 rename line.
- 2026-11-13: Keelson ships only as a Docker image on GHCR; nothing is published to npm, under either name, from 0.10. The image is Alpine with only the Node.js binary (no npm), built on the build machine's platform, with a size budget in CI. Running from a clone is for development. *Why:* the maintainer wants one way to run it that works the same everywhere, especially as Keelson starts to bundle other open-source scanners (Syft, Grype and the like), and a small image with fewer packages in it. Supersedes the npx distribution (2026-11-05), the wide `engines` range (2026-11-06) and the `edgewatch` npm package (2026-11-12).
- 2026-11-12: The nautical theme is used for module names and brand touches, each with a plain description beside it; platform, entity, account, location, check and finding stay plain. *Why:* the maintainer wants the theme to make Keelson stand out, but the people who read findings in an incident or an audit, or in a forwarded alert, shouldn't need a glossary, and the usual terms match each platform's own docs.
- 2026-11-12: Edgewatch is renamed Keelson (from 0.10). Old installations were to keep working through `EDGEWATCH_*` variables, the old folder, database, browser keys, npm package and image (all superseded 2026-11-13: removed, Edgewatch installations start fresh). The Docker image now sets only `KEELSON_INSTALL=docker` and defaults to `0.0.0.0` and `/data` in code, so a variable set on the container by either name wins. *Why:* the maintainer is taking it beyond the edge, to code, deployments, cloud logs, runtime and an AI pentester; the old name described only the first part.
- 2026-11-10: On phones, the platform picker and Run scan show icons only, and table headings never wrap. *Why:* the maintainer asked for layout glitches like these to be fixed; on a phone the entity's name was squeezed to nothing.
- 2026-11-10: Platform icons are the platforms' own monochrome marks (Cloudflare's cloud, Vercel's triangle, AWS's wordmark), replacing Phosphor's cloud, triangle and cube. *Why:* the maintainer asked for icons people recognise at a glance; the stand-ins looked close but not right.
- 2026-11-10: AWS is the third provider: one long-lived access key per account, signed GET requests only, its own request signing and XML reader instead of the AWS SDK. Services that only answer POST (CloudTrail, KMS, Config) are left unread. *Why:* the maintainer asked for AWS; GET-only keeps the hard rule intact without an exception, and no SDK keeps the install small. Verified against real accounts later the same day (see the line above).
- 2026-11-10: Everything the app says about a provider comes from `PROVIDER_INFO`, per-provider UI pieces are records keyed by provider ID, and no code compares a provider's name. Copy says "credential", or the provider's own word, instead of "token". *Why:* the maintainer asked for wording and code that stop assuming Cloudflare or Vercel, because more platforms are coming.
- 2026-11-10: AWS findings use the region as their `zone` ("Global" for IAM, S3 settings, CloudFront and Route 53), per-region settings are judged only where something runs, and a region that refuses the key is skipped rather than failing the scan. *Why:* a check that fires in every empty region gets ignored, and organizations close regions with service control policies.
- 2026-11-10: Checks that span providers now include AWS (`XP-004`, `XP-005`), and the scanner merges every `ProviderLinks` list generically. *Why:* a DNS record left pointing at a deleted CloudFront distribution, load balancer or bucket is a takeover neither dashboard shows.
- 2026-11-10: AWS checks were verified against the maintainer's two real accounts (every source readable), which showed three wrong ratings and one missing source: classic load balancers weren't read; a public database behind closed security groups was high; "no web ACL" fired on nearly every distribution; and "AWS address the entity doesn't hold" fired on two thirds of A records. They are now: read; medium; limited to distributions in front of an application; and split into "released" (seen to leave, high) and "outside the entity" (low). *Why:* findings must be right on real data, and a check that fires everywhere gets ignored.
- 2026-11-10: Deeper checks correlate across sources and providers instead of adding more single-setting checks: security groups are judged by what they are attached to, an internet-facing instance by its role, a Cloudflare-proxied hostname by its AWS origin's security group, a DNS record by whether its target still exists. A provider's scan receives its previous snapshot (`ScanInput.previous`) so it can report what changed, starting with released addresses. *Why:* the maintainer asked for checks that really improve a company's posture, and those are the ones no single dashboard shows.
- 2026-11-10: Instance start-up scripts are read and scanned for credentials in memory; only the kind found is stored. AWS's public address-range file is read without the access key. *Why:* credentials in user data are a common real leak, and Vercel's build commands already set the precedent of scanning text without keeping it.
- 2026-11-10: A list shared between accounts in an entity is only used when every account of the provider that publishes it supplied it. *Why:* on the first real scans, one AWS account was compared against a sibling that hadn't been scanned yet, and reported its load balancers as missing.
- 2026-11-10: One vocabulary for users (platform, entity, account, location, check, finding), platform icons on findings with a joined mark for correlations, and a sidebar split into Posture, Inventory, Insights and Manage. *Why:* the maintainer asked for terms people can tell apart, clear grouping in navigation and filters, and a visible sign of which platform a finding is from and which ones it correlates.
- 2026-11-10: The view pickers are tick boxes over one set of accounts, by entity and by platform, replacing the single-choice menus and the "All of <entity>" row. *Why:* the maintainer wants to tick an entity to get everything under it, and to leave out one of several accounts on a platform.
- 2026-11-10: A shared `.claude/settings.json` allows the safe development commands and denies release, sync and reading `.keelson/`. *Why:* contributors working with Claude Code shouldn't be asked to approve every test run, and no session should cut a release or read real tokens.
- 2026-11-10: This file separates rules for every session from the maintainer's own preferences, and gives contributors' agents a workflow: a branch on their fork, a pull request to `r4reetik/keelson`, decisions proposed in the pull request. *Why:* it was written as if every session were the maintainer's, so a contributor's agent would refuse to push to its own fork and record the contributor's preferences as the maintainer's.
- 2026-11-09: Vercel is the second provider, behind a `Provider` interface built for more (AWS, Google Cloud, Google Workspace…). Accounts record their provider; an entity can mix providers. *Why:* the maintainer runs Vercel next to Cloudflare and wants one place for both, with more platforms to come.
- 2026-11-09: Vercel tokens are accepted without a warning about their write access; Keelson only sends GET requests and never reads environment variable values. *Why:* Vercel has no read-only tokens, and the maintainer chose not to warn.
- 2026-11-09: The provider filter is part of the scope key and applies to every page; the Overview shows a score per provider next to the combined one. *Why:* the maintainer wants to see Cloudflare or Vercel findings on their own, and one filter that scales to many providers beats per-page filters.
- 2026-11-09: Checks that span providers (`XP-`) compare accounts within an entity, from the latest scans of the other accounts, and ship from the first Vercel release. *Why:* the problems between platforms (dangling records, WAF bypass through *.vercel.app) are the ones neither dashboard shows.
- 2026-11-09: Releases are cut on the maintainer's machine (`npm run release`) and only published by CI on the tag; `npm run sync` merges `origin/main` and repairs moved notes. *Why:* the workflow's commit to `origin/main` forked `main` on every release. 0.7.0 shipped without two unpushed commits, and pulls kept moving new notes under released versions. Supersedes the Actions → Release flow from 2026-11-05.
- 2026-11-09: Vercel checks were verified against the maintainer's real team, which corrected where managed rulesets are read and how unconfigured firewalls count. Checks that would fire on most projects of a normal team are limited to where they matter (bot protection on public sites only; AI crawlers, OWASP and rate limits once the firewall is being configured). *Why:* findings must be right on real data, and a check that fires everywhere gets ignored.
- 2026-11-09: Setup and Add accounts start with a platform choice. *Why:* people may use only one platform and shouldn't see the other's steps.
- 2026-11-08: This file is the single place for decisions and rules. `CLAUDE.md` imports it, and `test/agents.test.ts` checks that the paths, scripts and Node version it names are still right. *Why:* future work, by agents or people, should start from the decisions already made, and stay in sync with them.
- 2026-11-07: Free-text fields suggest values the app already knows: owners scoped to the entity, existing entity names, the current address for the Link URL. *Why:* a typed owner should match earlier spellings, and a duplicate entity is almost always a mistake.
- 2026-11-06: Node.js 26 LTS only, with a minimum of 26.13.0, and Node 24 dropped. *Why:* one supported line, and the maintainer asked for it. Supersedes the 24.x minimums from 2026-11-05.
- 2026-11-06 (superseded 2026-11-13: not on npm any more, so `engines` matches `MIN_NODE`): `engines` stays wide (`>=18`), and the real Node.js check runs first in `src/bin.ts`, with upgrade steps. *Why:* npm used `engines` to quietly serve 0.4.0 to older Node.js, and users should always get the newest Keelson.
- 2026-11-06: Run scan scans the current view, and a split menu offers the entity or every account in every entity. *Why:* it used to scan everything, across companies.
- 2026-11-06: The release script refuses to run when released notes moved, and docs pin the release line automatically. *Why:* a `git pull` merge moved 0.5.0's notes and broke the next release.
- 2026-11-05: Dependabot ignores major updates of `@types/node` and the `node` image. Actions moved to their latest majors, and Biome to 2.6. *Why:* the Node major changes on purpose, together with `NODE_MAJOR`.
- 2026-11-05: GitHub Sponsors are set up (`.github/FUNDING.yml`, `funding` in package.json, a README section).
- 2026-11-05: No total check count anywhere. *Why:* it goes stale with every new check.
- 2026-11-05: Releases come from GitHub Actions (superseded 2026-11-09: cut locally, published by Actions), with npm and Docker release lines safe to auto-update, update checks in the app, backups before migrations, and newer databases refused. *Why:* self-hosters need updates that are safe to take, and breaking changes need a warning.
- 2026-11-05: Distributed as both `npx keelson` and a Docker image (also runs on ECS); superseded 2026-11-13, Docker image only. *Why:* anyone should be able to start it with just a token. A Cloudflare Workers deployment was dropped.
- 2026-11-05: Multi-account with entities that may be separate legal entities, each with its own domains, alerts and inclusion in All accounts. A Triaged page follows every triaged finding over time. *Why:* the maintainer runs accounts for different companies.
- 2026-11-05: Cloudflare design language with Kumo, strict alignment and no AI-looking design. Finding dialogs are at least 75% wide. *Why:* the maintainer's requirement for the UI.
- 2026-11-05: Read-only by construction: GET and GraphQL queries only, skip what couldn't be read, and secrets kept outside the database. *Why:* it runs against production accounts with a read-only token.
